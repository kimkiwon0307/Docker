## 🐧 2.1 사전 기초 지식
도커(Docker)는 완전히 새로운 기술이 아니라, 사실 **리눅스(Linux) 운영체제의 커널 기능 위에서 동작**합니다. 따라서 운영체제, 프로세스, 격리 기술의 개념을 먼저 이해해야 합니다.

### 💻 2.1.1 운영체제와 커널의 개념
* **운영체제 (OS, Operating System) :** 컴퓨터의 한정된 하드웨어 자원을 효율적으로 관리하고 사용자 및 프로그램에 분배하는 최고 관리자입니다.
* **커널 (Kernel) :** 운영체제의 핵심 엔진(뇌)으로, CPU, 메모리, 디스크 등의 하드웨어를 직접 제어하고 조율하는 역할을 합니다.
* **운영체제의 5대 핵심 역할 :**
  1. **프로세스 관리 :** 프로그램의 실행, 스케줄링, 종료 제어
  2. **메모리 관리 :** 프로그램(프로세스)마다 독립된 가상 메모리 공간 분리 및 할당
  3. **파일 시스템 관리 :** 디스크 내부의 파일 저장, 읽기, 권한 관리
  4. **네트워크 관리 :** 소켓 통신 및 인터넷 데이터 패킷 처리
  5. **사용자 관리 :** 다중 사용자 환경에서의 권한(Permission) 및 보안 통제
> 💡 **도커와 리눅스의 관계 :** 도커 컨테이너도 결국 운영체제가 실행하고 관리하는 **하나의 격리된 프로세스**일 뿐입니다. 도커가 리눅스 기반에서 태어난 이유는 도커를 지탱하는 핵심 격리 기술(`Namespace`, `cgroups`)이 리눅스 커널의 고유 기능이기 때문입니다.

### ⚙️ 2.1.2 프로그램, 프로세스, 스레드
* **프로그램 (Program) :** 디스크에 저장되어 있는 실행 전 상태의 정적 파일 (예: `nginx.exe`, 소스코드 빌드 파일)
* **프로세스 (Process) :** 프로그램이 메모리에 적재되어 **현재 실행 중인 상태**입니다. 운영체제는 프로세스마다 고유한 PID(프로세스 ID)를 부여하고, 전용 메모리 공간과 CPU 자원을 분배합니다. **(도커 컨테이너는 격리된 프로세스입니다)**
* **스레드 (Thread) :** 프로세스 내부에서 실제로 작업을 수행하는 **최소 실행 단위**입니다. 하나의 프로세스(회사) 안에 여러 스레드(직원)가 메모리를 공유하며 병렬 처리를 수행할니다.

### 🚧 2.1.3 네임스페이스(Namespace)와 자원 제한(cgroups)
컨테이너가 마치 독립된 하나의 가상 서버처럼 작동할 수 있는 비밀은 리눅스 커널의 두 가지 기술 덕분입니다.

1. **네임스페이스 (Namespace) :** 특정 프로세스에게 물리 호스트의 자원을 다 보여주지 않고, **"너만의 가상 세계"를 만들어 시야를 격리하는 기술**입니다.
   * **PID Namespace :** 프로세스 트리를 격리합니다. 컨테이너 내부의 메인 프로세스는 스스로 PID 1번으로 인식합니다.
   * **Network Namespace :** 네트워크 스택을 격리하여 컨테이너마다 고유한 독립 가상 IP, 포트 번호, 라우팅 테이블을 가집니다.
   * **Mount (mnt) Namespace :** 파일 시스템 마운트 지점을 격리하여 컨테이너가 호스트와 다른 독자적인 디렉토리 구조를 보게 합니다.
   * **UTS Namespace :** 독립적인 호스트 이름(Hostname)과 도메인 이름을 부여합니다.
   * **IPC Namespace :** 프로세스 간 통신(Shared Memory 등) 통로를 컨테이너 별로 분리합니다.
2. **cgroups (Control Groups - 내용 보완) :** 네임스페이스가 시야를 격리한다면, cgroups는 자원의 양을 통제합니다. 특정 컨테이너가 호스트의 CPU나 메모리를 과도하게 점유하여 다른 서비스에 피해를 주지 않도록 **자원의 최대 사용 한도(CPU 코어 수 제한, 메모리 1GB 제한 등)를 강제하는 기술**입니다.

### 🐳 2.2.4 도커 기초 지식

### 📦 2.2.1 도커(Docker)의 정의와 목표
* **정의 :** 애플리케이션과 이를 실행하는 데 필요한 모든 환경(라이브러리, 의존성 파일, 설정 값 등)을 **컨테이너라는 표준화된 형태로 패키징하고 배포·실행하는 오픈소스 플랫폼**입니다.
* **핵심 목표 :** 어디서나 동일한 실행 환경 보장(이식성), 가볍고 빠른 배포, 인프라 운영 자동화 극대화.

### 🛡️ 2.2.2 컨테이너(Container)의 핵심 특징
* **격리성 :** 하나의 물리 서버 안에서 여러 개의 컨테이너(Nginx, MySQL, Redis 등)가 서로의 파일이나 네트워크를 전혀 침범하지 않고 독립 실행됩니다.
* **경량성 :** 호스트의 커널을 그대로 공유하기 때문에 구조적으로 무겁지 않습니다.
* **빠른 속도 :** OS 부팅 과정이 필요 없으므로, 프로세스가 켜지는 속도(수밀리초)와 동일하게 즉시 실행됩니다.
* **이식성 :** "내 컴퓨터에서는 잘 되는데 서버에선 왜 안 되지?"라는 고질적인 환경 문제를 완벽히 해결합니다. 도커만 깔려 있다면 로컬, 스테이징, 운영 클라우드 환경 어디서든 100% 동일하게 작동합니다.

### ⚖️ 2.2.3 가상화 모델 비교 (VM vs 컨테이너)
하나의 물리 서버를 쪼개어 가상 공간을 만든다는 목적은 같지만 가상화의 깊이가 다릅니다.



#### 1) 하이퍼바이저 가상화 (VM)
* **구조 :** `물리 하드웨어` $\rightarrow$ `하이퍼바이저(Hypervisor)` $\rightarrow$ **`Guest OS (가상 운영체제)`** $\rightarrow$ `애플리케이션(App)`
* **특징 :** 하드웨어 자체를 가상화합니다. 가상머신마다 독립된 OS(kernel 포함)를 통째로 부팅시켜야 하므로 기가바이트(GB) 단위로 무겁고, 부팅 속도가 수 분 걸리며 CPU/메모리 오버헤드가 큽니다.

#### 2) 컨테이너 가상화 (Docker)
* **구조 :** `물리 하드웨어` $\rightarrow$ `Host OS` $\rightarrow$ `도커 엔진(Docker Engine)` $\rightarrow$ **`컨테이너 (커널 공유)`**
* **특징 :** OS 레벨 가상화입니다. 호스트 리눅스의 커널 엔진을 모든 컨테이너가 완벽히 공유하고, 네임스페이스로 격리만 해두었기 때문에 메가바이트(MB) 단위로 매우 가볍고 시작과 종료가 즉시 이루어집니다.

### 🛠️ 2.2.4 도커 핵심 구성 요소와 실무 워크플로우

### 1️⃣ 도커 클라이언트 (Docker Client)
* 사용자가 터미널 창에 `docker run`, `docker build`와 같은 도커 명령어를 입력하는 인터페이스 창구입니다. 이 명령은 도커 데몬(엔진)에 API 형태로 전달됩니다.

### 2️⃣ 도커 엔진 / 데몬 (Docker Engine / Daemon - `dockerd`)
* 백그라운드에서 상시 작동하며 실제 무거운 일을 도맡아 하는 핵심 엔진입니다. 이미지 관리, 컨테이너 생성 및 실행 제어, 네트워크 장치 연결, 스토리지 볼륨 관리 등을 책임집니다.

### 3️⃣ 도커 이미지 (Docker Image)
* 컨테이너를 실행하기 위해 필요한 모든 파일과 설정, 라이브러리를 압축해 놓은 **정적 읽기 전용(Read-Only) 템플릿**입니다. (클래스와 객체 관계에서 '클래스'에 비유)

### 4️⃣ 도커 컨테이너 (Docker Container)
* 도커 이미지를 기반으로 메모리에 올려 **실제 살아 움직이게 만든 실행 상태(Instance)**입니다. 컨테이너가 구동되면 이미지 레이어 위에 독립된 읽기/쓰기(Read-Write) 레이어가 한 층 더해져 데이터를 변경하거나 저장할 수 있게 됩니다.

### 5️⃣ 도커 레지스트리 (Docker Registry)
* 빌드가 완료된 도커 이미지들을 중앙에서 업로드하고 다운로드할 수 있는 **이미지 저장소 라이브러리**입니다. 전 세계 표준 공용 저장소인 **도커 허브(Docker Hub)**가 대표적이며, 기업 내부용 사설 레지스트리(AWS ECR 등)를 구축하기도 합니다.

### 📋 3.1 사전 준비 사항
도커를 안전하게 설치하고 운용하기 위해, 본격적인 설치 전 아래 6가지 요구사항을 체크합니다.

1. **Ubuntu 버전 확인 :** 도커는 최신 리눅스 커널 환경에서 가장 안정적입니다. (우분투 LTS 버전 권장)
   * 확인 명령어: cat /etc/os-release

2. **sudo 권한 확인 :** 패키지 제어 및 가상 네트워크 장치 생성을 위해 관리자(root) 권한이 반드시 필요합니다.
   * 확인 명령어: sudo whoami (결과가 root로 나와야 합니다.)

3. **인터넷 연결 상태 :** Docker 공식 APT 저장소로부터 대용량 패키지를 다운로드해야 하므로 외부 인터넷망 연결이 필수적입니다.

4. **디스크 여유 공간 :** 도커 이미지, 컨테이너 레이어, 볼륨 데이터가 지속적으로 쌓이므로 루트 패치에 최소 수 GB 이상의 디스크 용량을 확보해야 합니다.

5. **메모리 제원 :** 다중 컨테이너 및 고부하 애플리케이션(DB, 웹 서버 등)의 원활한 병렬 구동을 위해 최소 **8GB 이상**의 RAM 시스템 환경을 권장합니다.

6. **CPU 가상화 활성화 :** 호스트 운영체제(OS) 수준에서 컨테이너 프로세스를 효율적으로 격리·구동할 수 있도록 CPU 가상화 기능(Intel VT-x / AMD-V)이 켜져 있어야 합니다.

### 🛠️ 3.2 도커 설치
리눅스는 가상 OS를 거치지 않고 Docker가 호스트 커널을 직접 사용할 수 있으므로, Ubuntu 환경에서는 가벼운 'Docker Engine'만 설치하여 사용하는 것이 일반적입니다.

1. **패키지 목록 업데이트 :** sudo apt update
2. **기존 구버전 Docker 제거 :** sudo apt remove docker docker-engine docker.io containerd runc
   * 구버전 패키지가 남아있으면 설치 충돌이 발생할 수 있으므로 사전에 정리합니다.
3. **필수 패키지 설치 :** sudo apt install -y ca-certificates curl gnupg
   * Docker 저장소의 보안 인증 및 암호화 키를 다루기 위한 필수 도구입니다.
4. **Docker GPG Key 등록 :**
   ```bash
  sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg
  ```
   * 💡 GPG Key란? 패키지 위변조를 방지하기 위해 진짜 Docker 공식 저장소에서 제공하는 안전한 패키지가 맞는지 검증하는 인증서입니다.

5. **Docker Repository 등록 :** *
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] [https://download.docker.com/linux/ubuntu](https://download.docker.com/linux/ubuntu) $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
   * 💡 Repository 등록이란? Ubuntu 시스템의 패키지 매니저(apt)에게 "앞으로 소프트웨어를 다운로드할 때 Docker 공식 저장소 경로도 함께 조회해라"라고 등록해 주는 과정입니다.

6. **패키지 목록 갱신 :** sudo apt update
   * 새로 등록한 Docker 저장소의 최신 패키지 정보를 시스템에 반영합니다.

7. **Docker 엔진종류 최종 설치 :
    sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

📑 설치되는 핵심 구성 요소 역할:
* **docker-ce :** 도커 엔진 (실제 컨테이너를 구동하고 백그라운드에서 관리하는 핵심 데몬)
* **docker-ce-cli :** 도커 명령어 도구 (사용자가 터미널 창에 명령어를 입력할 수 있게 해주는 인터페이스)
* **containerd.io :** 컨테이너 런타임 (리눅스 커널 기능을 직접 활용해 프로세스를 격리하는 실구동부)
* **buildx-plugin :** 고급 빌드 기능 (다양한 CPU 아키텍처 환경에 맞춰 이미지를 빌드하는 확장 도구)
* **compose-plugin :** Docker Compose 기능 (여러 개의 컨테이너 환경을 하나의 파일로 묶어 일괄 제어)

8. **설치 상태 최종 확인 :** docker version
   * 🚨 permission denied 에러 발생 시 해결법: Docker 데몬은 기본적으로 관리자(root) 권한으로 구동되므로 일반 계정에서는 소켓 접근 권한이 거부됩니다. 현재 사용자를 docker 그룹에 영구 추가하여 해결합니다.
   * 해결 방법: sudo usermod -aG docker $USER 입력 후, 'newgrp docker'를 입력하거나 세션을 재접속합니다.
   * 최종 검증: 'docker ps'로 정상 작동을 확인하고, 'systemctl status docker'로 서비스 구동 상태를 체크합니다.

### 🚀 3.3 Hello-World 및 Nginx 첫 실습
도커가 정상적으로 설치되었다면 기본 이미지들을 활용해 컨테이너의 핵심 작동 원리를 파악합니다.

#### 🧪 3.3.1 hello-world 실행 시 내부 작동 메커니즘
* 실행 명령어: docker run hello-world

도커는 철저히 이미지 기반으로 동작하며, run 명령 한 번에 pull(다운로드), create(생성), start(실행) 과정이 모두 포함되어 있습니다. 내부적으로는 아래 7단계의 순서대로 일어납니다.
1. **로컬 창고 수색 :** 내 컴퓨터(로컬) 환경에 hello-world 이미지가 이미 다운로드되어 있는지 확인합니다.
2. **원격 저장소 접속 :** 로컬에 파일이 없다면 인터넷망을 통해 글로벌 공용 저장소인 도커 허브(Docker Hub)에 접속합니다.
3. **이미지 다운로드 (Pull) :** 도커 허브로부터 최신 hello-world 이미지를 안전하게 다운로드합니다.
4. **컨테이너 공간 생성 (Create) :** 다운로드한 정적 이미지를 바탕으로 독립된 격리 샌드박스 공간을 개설합니다.
5. **프로세스 실행 (Start) :** 컨테이너 내부의 메인 애플리케이션 프로세스를 가동합니다.
6. **메시지 출력 :** 화면에 환영 문구(Hello from Docker!)를 출력합니다.
7. **프로세스 및 컨테이너 종료 :** 텍스트 출력이 완료되어 내부 메인 프로세스가 끝나면, 컨테이너도 자원을 반납하며 그 즉시 자동 종료(Exited) 상태로 전환됩니다.

📌 컨테이너 생명주기 확인 가이드:
* 컨테이너는 내부에 켜진 메인 프로세스가 죽으면 가동을 멈춥니다.
* 현재 실행 중인 실시간 컨테이너 확인: docker ps
* 가동이 끝나고 종료된 컨테이너까지 전체 내역 확인: docker ps -a

#### 🌐 3.3.2 nginx 웹 서버 실시간 백그라운드 가동 실습
웹 서버처럼 종료되지 않고 상시 켜져서 외부 트래픽을 대기해야 하는 서비스는 아래 옵션을 조합하여 실행합니다.

* 실행 명령어: docker run -d -p 80:80 --name my-web nginx

💡 핵심 실행 옵션 상세 분석:
* **-d (Detached 모드) :** 컨테이너를 백그라운드(화면 뒤편)에서 조용히 실행하도록 만듭니다. 이 옵션이 있어야 웹 서버가 켜진 상태에서도 터미널 창이 먹통이 되지 않고 다음 명령어를 연속해서 입력할 수 있습니다.
* **-p 80:80 (포트 포워딩) :** 외부 호스트의 포트와 컨테이너 내부의 전용 포트를 1:1로 단단히 연결합니다. 외부 사용자가 내 서버 IP의 80번 포트로 접속하면, 도커 엔진이 컨테이너 내부 샌드박스의 80번 포트로 트래픽을 안전하게 중계(릴레이)해 줍니다.
* **nginx :** 웹 서버 구동을 위해 도커 허브로부터 불러올 표준 웹 서버 베이스 이미지 명칭입니다.

</details>

<summary><kbd>📁 4장. 도커 기초 (클릭하여 펼치기)</kbd></summary>

> **Docker**는 이미지를 이용해 컨테이너를 실행하는 기술입니다.

---

### 4.1 도커 기초 개념

#### 4.1.1 도커 동작 방식
1. **사용자**: 터미널을 통해 명령어를 입력합니다.
2. **Docker Client**: 사용자가 입력한 명령어(ex. `docker run`, `docker ps`, `docker images`)를 받아 Docker Engine에 전달합니다.
3. **Docker Engine**: 도커의 실제 핵심 엔진입니다. 명령을 받아 이미지 관리, 컨테이너 생성, 네트워크 및 볼륨 생성 등의 실질적인 작업을 수행합니다.
4. **이미지 확인**: 실행하려는 이미지가 로컬에 있는지 확인합니다.
5. **컨테이너 생성**: 이미지를 기반으로 독립된 컨테이너 공간을 만듭니다.
6. **프로세스 실행**: 컨테이너 내부에서 애플리케이션 프로세스를 구동합니다.

---

#### 4.1.2 도커 이미지 (Docker Image)
> 💡 **이미지란?** 도커에서 가장 중요한 개념으로, 컨테이너의 **'설계도'**라고 부릅니다.
> * **비유:** 도커 이미지(`붕어빵 틀`) ◀─▶ 도커 컨테이너(`붕어빵`)
> * *ex) nginx 이미지 안에는 nginx 프로그램, 필요한 라이브러리, 설정 파일이 모두 포함되어 있습니다.*

* **📌 이미지의 주요 특징**
    1. **읽기 전용 (Read-Only):** 이미지는 한 번 생성되면 수정되지 않습니다.
    2. **다중 컨테이너 생성 가능:** 하나의 동일한 이미지로 여러 개의 독립된 컨테이너를 동시에 생성할 수 있습니다.

---

#### 4.1.3 도커 컨테이너 (Docker Container)
> 💡 **컨테이너란?** 이미지를 실행한 **'결과물'**입니다.
> `docker run nginx`를 실행하면 [ nginx 이미지 ] ──> [ 컨테이너 생성 ] ──> [ nginx 프로세스 실행 ] 단계를 거칩니다.

* **💻 가상머신(VM) vs 컨테이너**
    * **VM:** 각 가상머신마다 독립된 OS(Guest OS)를 통째로 포함하여 무겁습니다.
    * **Container:** Host 리눅스 커널을 공유하며, VM이 아니라 호스트 OS단에서 **격리된 프로세스**로 동작합니다.
    * *따라서 Ubuntu 서버에서 `docker run nginx`를 실행하는 것은 실제 Linux 내부에서 격리된 nginx 프로세스를 실행하는 것과 같습니다.*

* **📌 컨테이너의 주요 특징**
    1. **독립성:** 각 컨테이너는 자신만의 독립된 파일 시스템을 사용합니다.
    2. **격리성:** 프로세스 단위로 철저히 분리되어 서로 영향을 주지 않습니다.
    3. **이식성:** 환경에 구애받지 않고 어디서나 동일하게 실행됩니다.
    4. **빠른 시작:** OS 부팅 과정이 없으므로 수 초 이내에 가동됩니다.

---

#### 4.1.4 Hello-World 실행 과정 상세
`docker run hello-world` 명령어가 처리되는 전체 생명주기(Lifecycle)는 다음과 같습니다.

1. **사용자 입력:** `docker run hello-world` 실행
2. **Docker Engine 확인:** 로컬에 `hello-world` 이미지가 있는지 검사
3. **Docker Hub 접속:** 로컬에 이미지가 없다면 인터넷을 통해 도커 공식 이미지 저장소(Docker Hub)에 접속
4. **이미지 다운로드:** 저장소로부터 `hello-world` 이미지 다운로드 (`image pull`)
5. **컨테이너 생성:** 다운로드한 이미지를 기반으로 컨테이너 공간 개설 (`image -> container`)
6. **프로세스 실행:** 컨테이너 내부에서 `hello-world` 프로그램 가동
7. **메시지 출력:** 화면에 `Hello from Docker!` 환영 문구 출력
8. **프로세스 종료:** 프로그램 실행 및 출력 작업 완료
9. **컨테이너 종료:** 메인 프로세스가 종료됨에 따라 컨테이너도 즉시 자동 종료

### 4.2 도커 기초 명령어

#### 4.2.1 도커 이미지 다운로드
> 💡 **이미지(Image)란?** 컨테이너를 생성하기 위한 **'독립된 설계도'**입니다.

* **명령어:** `docker pull nginx`
* **확인 명령어:** `docker images`

##### 📊 이미지 다운로드 내부 동작 흐름
사용자가 터미널에 다운로드 명령을 내린 후, 로컬 PC에 저장되기까지의 전체 흐름도입니다.

### 4.2 도커 기초 명령어

#### 4.2.1 도커 이미지 다운로드
> 💡 **이미지(Image)란?** 컨테이너를 생성하기 위한 독립된 **'설계도'**입니다.

* **Nginx 이미지 다운로드 명령어:** `docker pull nginx`
* **다운로드 완료 확인 명령어:** `docker images`

* **⚙️ 이미지 다운로드 내부 동작 흐름**
  사용자 명령어 입력 (`docker pull nginx`) ──> 외부 도커 허브(`Docker Hub`) 접속 ──> nginx 이미지 다운로드 ──> 로컬 PC 저장소(`Local Registry`) 저장 완료

#### 4.2.2 도커 이미지 상세 구조
* **Nginx 이미지는 무엇으로 구성될까?**
  * 실제로는 **Linux OS 일부 + nginx 프로그램 + 라이브러리 + 설정 파일**이 합쳐진 파일입니다.

* **🧱 도커 이미지의 핵심: 레이어(Layer) 구조**
  * 도커 이미지는 한 번에 만들어지는 것이 아니라 설계 단계가 차곡차곡 쌓이는 **Layer 구조**를 가집니다.
  * *예시: Ubuntu 베이스 다운로드 ──> nginx 프로그램 설치 ──> 환경 설정 추가*
  * **레이어 확인 명령어:** `docker history nginx`

* **❓ 레이어 구조가 왜 중요할까? (이미지 재사용)**
  * 동일한 베이스를 가진 이미지는 해당 레이어를 **공유**합니다. 예를 들어 Ubuntu 기반 이미지 100개가 있더라도 로컬 PC에는 Ubuntu 레이어가 단 1개만 저장되므로 전체 용량을 획기적으로 절약할 수 있습니다.

---

#### 4.2.3 도커 이미지 목록 확인
* **기능:** 현재 내 PC(호스트) 저장소에 다운로드되어 있는 이미지 목록을 조회합니다.
* **명령어:** `docker images` 또는 `docker image ls`

---

#### 4.2.4 도커 컨테이너 실행
* **기본 실행:** `docker run nginx`
  * **⚙️ 내부 실행 순서:** 로컬 PC에서 이미지 존재 확인 ──> 컨테이너 격리 공간 생성 ──> nginx 프로세스 실행

* **주요 실행 옵션 활용:**
  * **백그라운드 실행 (`-d`):** `docker run -d nginx`
    * *Detached 모드로 실행하여, 컨테이너가 켜진 후에도 터미널 창을 계속 사용할 수 있게 합니다.*
  * **포트 연결 (`-p`):** `docker run -d -p 80:80 nginx`
    * *외부에서 접속할 수 있도록 호스트 PC의 80번 포트와 컨테이너 내부의 80번 포트를 다리로 연결(포트 포워딩)합니다.*
  * **이름 지정 (`--name`):** `docker run -d --name my-nginx nginx`
    * *도커가 자동으로 부여하는 랜덤 이름 대신, 관리가 편하도록 `my-nginx`라는 직관적인 이름을 부여합니다.*

 #### 4.2.5 도커 컨테이너 목록 확인
* **실행 중인 컨테이너만 조회:** `docker ps`
* **종료된 컨테이너를 포함한 전체 조회:** `docker ps -a`

---

#### 4.2.6 컨테이너 내부 접속
* **기능:** `exec` 명령어를 통해 실행 중인 컨테이너 내부로 들어가 직접 리눅스 명령을 실행합니다.
* **기본 접속 명령어:** `docker exec -it my-nginx bash`
  * *내부 진입 후 명령어 예시:*
    * 파일 확인: `ls`
    * 프로세스 확인: `ps -ef`
    * 컨테이너 밖으로 나가기(종료): `exit`
* **💡 Tip (bash가 없을 경우):** 이미지에 따라 `bash` 쉘이 없을 수 있습니다. 이럴 때는 대안 쉘인 `sh`를 사용합니다.
  * `docker exec -it 컨테이너명 sh`

---

#### 4.2.7 컨테이너 삭제
* **정석적인 방법 (중지 후 삭제):**
  1. 컨테이너 중지: `docker stop my-nginx`
  2. 컨테이너 삭제: `docker rm my-nginx`
* **한 번에 강제 삭제 (`-f`):** `docker rm -f my-nginx`
  * *실행 중인 컨테이너를 정지함과 동시에 바로 삭제합니다.*

---

#### 4.2.8 이미지 삭제
* **목록 확인:** `docker images`
* **이미지 삭제 명령어:** `docker rmi nginx` 또는 `docker image rm nginx`
* **⚠️ 주의:** 해당 이미지를 참조하거나 사용 중인 컨테이너가 하나라도 존재하면 삭제가 불가능합니다. (반드시 컨테이너 먼저 삭제 필요)

---

#### 4.2.9 도커 이미지 변경
* **태그(버전) 변경 명령어:** `docker tag nginx my-nginx:v1`
* **특징:** 이미지 ID는 같지만 다른 이름을 가진 '명찰'을 하나 더 다는 개념입니다. 실무에서 빌드된 이미지의 버전을 체계적으로 관리할 때 필수적으로 이용합니다.

---

### 🗂️ 도커 명령어 치트시트 모음

#### 4.2.10 도커 이미지 명령어 모음
* 📥 **다운로드:** `docker pull nginx` (도커 허브에서 이미지 가져오기)
* 📋 **목록 조회:** `docker images` (로컬 PC에 저장된 이미지 확인)
* 🔍 **상세 구조:** `docker history nginx` (이미지 빌드 레이어 확인)
* 🏷️ **태그 변경:** `docker tag nginx my-nginx:v1` (이미지 버전 명찰 추가)
* ❌ **이미지 삭제:** `docker rmi nginx` (컨테이너 미사용 시 삭제 가능)

#### 4.2.11 도커 컨테이너 명령어 모음
* 🚀 **컨테이너 실행:** `docker run nginx` (전면 실행)
* 🔄 **백그라운드 실행:** `docker run -d nginx` (숨김 실행)
* 🟢 **실행 목록:** `docker ps` (현재 가동 중인 컨테이너 확인)
* 📜 **전체 목록:** `docker ps -a` (종료된 컨테이너 포함 확인)
* 💻 **내부 접속:** `docker exec -it 컨테이너명 bash` (컨테이너 안으로 진입)
* 📝 **로그 확인:** `docker logs <컨테이너명>` (컨테이너 내부 출력 결과물 확인)
* 🛑 **실행 중지:** `docker stop <컨테이너명>` (안전하게 프로세스 종료)
* 🗑️ **컨테이너 삭제:** `docker rm <컨테이너명>` (격리 공간 데이터 삭제)


### 4.3 도커 컨테이너 네트워크

도커는 호스트 서버(내 컴퓨터) 안의 격리된 독립적인 네트워크 공간에서 실행됩니다.

#### 4.3.1 도커 컨테이너 네트워크 구조
* **컨테이너 고유 IP 부여:** 각 컨테이너는 호스트와 분리된 자신만의 고유한 내부 IP를 가집니다.
  * 컨테이너 실행 예시: `docker run -d --name web nginx`
  * 컨테이너 내부 IP 확인: `docker exec -it web bash` 진입 후 `ip addr` 입력 (결과 예시: 172.17.0.2)

* **도커 네트워크 아키텍처 기본 구조:**
  * 구조 형태: [Ubuntu Host] ➔ [docker0 가상 스위치] ➔ [Container A, B, C]
  * **docker0:** 도커를 설치하면 시스템에 자동으로 생성되는 '가상 네트워크 스위치(브리지)'입니다. (확인 명령어: `ip addr show docker0`)

* **컨테이너 간의 통신:**
  * 동일한 호스트 내에 생성된 컨테이너들은 `docker0`라는 같은 가상 네트워크 대역에 묶이므로 서로 통신이 가능합니다. (ex. web 컨테이너 172.17.0.2 ➔ db 컨테이너 172.17.0.3 통신 가능)

* **컨테이너 내부에서 localhost가 안 되는 이유:**
  * 컨테이너 내부에서의 `localhost`나 `127.0.0.1`은 외부 호스트 PC가 아니라, **컨테이너 자기 자신**을 가리키기 때문입니다. 즉, web 컨테이너 안의 localhost는 web 컨테이너 자체일 뿐이므로 db 컨테이너와 연결되지 않습니다.

* **포트 매핑 (Port Mapping):**
  * 외부에서 컨테이너 내부 서비스에 접근할 수 있도록 호스트의 포트와 컨테이너의 포트를 연결해 주는 기술입니다.
  * 실행 예시: `docker run -d -p 80:80 nginx` (호스트의 80번 포트와 컨테이너의 80번 포트 연결)
  * 실제 트래픽 흐름: 외부 브라우저 ➔ Ubuntu 호스트(80번 포트) ➔ Docker NAT 인터페이스 ➔ 컨테이너(80번 포트) ➔ 웹 접속 성공 (http://localhost 가능)

* **직관적인 네트워크 비유:**
  * **Ubuntu 서버** = 하나의 거대한 아파트
  * **docker0** = 아파트 층마다 있는 공용 복도
  * **컨테이너** = 복도를 통해 연결된 각각의 집들
  * 각 집(컨테이너)은 문패와 호수(자기 주소 및 IP)를 따로 가지고 있으며, 공용 복도(docker0)를 통해서 옆집과 자유롭게 소통합니다.


#### 4.3.2 도커 네트워크 확인 및 종류
* **도커 네트워크 목록 조회:** `docker network ls`
* **도커의 주요 기본 네트워크 종류:**
  * **bridge:** 도커의 기본 네트워크 방식으로, `docker0` 가상 스위치를 통해 호스트 및 컨테이너 간 통신을 연결합니다.
  * **host:** 컨테이너가 독립된 네트워크 공간을 갖지 않고, 호스트 서버의 네트워크 환경을 그대로 함께 공유하여 사용합니다.
  * **none:** 네트워크를 완전히 사용하지 않는 격리 상태입니다.
* **네트워크 상세 정보 확인:** `docker network inspect bridge`
  * 해당 네트워크의 IP 서브넷 대역, 연결된 컨테이너 목록, 게이트웨이(Gateway) 주소 등을 상세히 조회할 수 있습니다.
* **특정 컨테이너의 IP 직접 확인:** `docker inspect web | grep IPAddress`

#### 4.3.3 호스트에서 컨테이너로 파일 전송 (Host ➔ Container)
* **개념:** 우분투 호스트 서버에 있는 설정 파일이나 웹 소스 코드 등을 실행 중인 컨테이너 내부의 특정 경로로 복사하여 전달합니다.
* **명령어:** `docker cp index.html web:/tmp`
  * *설명:* 호스트의 `index.html` 파일을 `web` 컨테이너의 `/tmp` 디렉터리로 복사합니다.
* **전송 구조:** Ubuntu Host ➔ `docker cp` ➔ Container
* **실무 검증 방법:** 파일이 누락 없이 잘 복사되었는지 컨테이너에 직접 들어가지 않고 밖에서 바로 확인하는 명령어로 검증합니다.
  ```bash
  docker exec -it web ls -l /tmp
  ```
#### 4.3.4 컨테이너에서 호스트로 파일 전송 (Container ➔ Host)
* **개념:** 컨테이너 내부에서 생성된 데이터(예: 데이터베이스 백업 파일, 프로그램 로그 등)를 안전하게 보관하거나 분석하기 위해 외부 호스트 서버로 복사하여 가져옵니다.
* **명령어:** `docker cp web:/tmp/backup.sql .`
  * *설명:* `web` 컨테이너 내부 `/tmp/backup.sql` 파일을 호스트의 현재 디렉터리(`.`)로 복사합니다. 맨 뒤의 마침표(`.`)는 현재 위치를 뜻하므로 생략하면 안 됩니다.
* **전송 구조:** Container ➔ `docker cp` ➔ Ubuntu Host
* **💡 실무 한스푼 팁:** 컨테이너는 삭제되면 내부의 데이터도 함께 사라지는 일회성 특징을 가집니다. 따라서 중요한 데이터베이스 백업(`vmdump`, `mysqldump` 등)을 수행한 후에는 반드시 이 명령어를 사용해 호스트 서버나 별도의 스토리지로 파일을 안전하게 빼내야 합니다.
    
#### 4.4 도커 스토리지

##### 4.4.1 도커 스토리지의 개념
컨테이너 내부에서 파일을 생성하면 어디에 저장되고 어떻게 관리될까?

* **실험 예시:** 우분투 테스트 컨테이너 내부로 진입한 뒤, `echo "hello" > test.txt` 명령어를 실행하여 파일 시스템에 파일 생성
* **결과와 문제점:** 생성된 `test.txt` 파일은 외부 호스트 PC가 아닌, 오직 **컨테이너 내부 파일시스템**에만 존재합니다.

---

##### 4.4.2 컨테이너 파일 시스템 특징

> ⚠️ **핵심 요약: 컨테이너 내부 저장소는 영구 저장소(Persistent Storage)가 아닙니다.**

* **독립된 격리 구조:**
  ```text
  [ Container 격리 공간 ]  ➔ 컨테이너 전용 개별 공간
      ├── /etc
      ├── /var
      ├── /tmp
      └── test.txt (새로 생성된 파일)
  ```
* **데이터 휘발성 문제:** 컨테이너를 정지하더라도 데이터는 유지되지만, 컨테이너를 삭제하는 순간 내부 파일시스템이 함께 통째로 삭제되며 데이터도 영구히 손실됩니다.

##### 4.4.2 도커 스토리지의 필요성
만약 MySQL 컨테이너에 중요한 데이터베이스 데이터를 저장한 상태로 컨테이너를 삭제하면 어떻게 될까? 데이터가 모두 증발하여 심각한 서비스 장애로 이어집니다. 

이러한 문제를 해결하기 위해 **컨테이너 외부(호스트 서버)에 데이터를 안전하게 보관하는 기술**이 필요합니다.

* **개념:** 컨테이너와 호스트 스토리지(Host Storage)를 서로 연결하는 것
* **도커에서의 명칭:** **마운트(Mount)**
* **도커 스토리지의 종류:**
  1. **Volume** (도커가 직접 관리)
  2. **Bind Mount** (호스트의 특정 디렉터리 연결)
  3. **Tmpfs Mount** (메모리 영역 저장)
  > 💡 **실무 팁:** 실제 운영 환경 및 실무에서는 주로 **Volume**과 **Bind Mount**를 사용합니다.

  ##### 4.4.3 Volume
도커(Docker)가 직접 호스트 파일 시스템의 일부분을 제어하고 관리하는 스토리지 방식입니다.

* **구조:** `Container` ➔ `Volume` ➔ `Host Disk`
* **실제 저장 위치 (Ubuntu):** `/var/lib/docker/volumes/`
* **장점:** 도커가 데이터 영역을 직접 관리하므로 안전하며, 호스트 파일 시스템과 격리되어 있어 관리가 용이합니다.

<h6>주요 명령어 및 사용법</h6>

* **볼륨 생성, 확인 및 사용 예시**
  my-volume이라는 이름의 볼륨 생성
  > docker volume create my-volume

  생성된 볼륨 목록 확인 (출력 결과: my-volume)
  > docker volume ls

  볼륨의 상세 정보 및 실제 호스트 경로 확인
  > docker volume inspect my-volume

  기본 사용 예시: 호스트의 my-volume을 컨테이너 내부의 /data 디렉터리와 마운트
  > docker run -d -v my-volume:/data ubuntu

  실무 적용 예시 (MySQL 데이터 보존)
  > docker run -d -v mysql-data:/var/lib/mysql mysql

  * **의미:** 호스트 볼륨(`my-volume`)과 컨테이너 내부의 지정된 경로(`/data`)를 연결합니다.
  * **결과:** 컨테이너를 영구 삭제하더라도 데이터베이스 데이터는 호스트의 `mysql-data` 볼륨에 그대로 유지되므로 안전하게 서비스를 재시작할 수 있습니다.

  ##### 4.4.4 Bind Mount
호스트 컴퓨터의 특정 디렉터리를 컨테이너 내부 경로와 직접 연결하는 스토리지 방식입니다.

* **구조:** `Host (/home/user/project)` ➔ (연결) ➔ `Container (/app)`
* **특징:** 호스트와 컨테이너 간의 **실시간 양방향 동기화**가 이루어집니다. (호스트에서 수정하면 컨테이너에 즉시 반영되며, 반대의 경우도 마찬가지입니다.)
* **장점:** 호스트에서 직접 폴더를 확인할 수 있어 데이터 백업이 쉽고, 변경 사항이 실시간으로 반영됩니다.
* **단점:** 특정 호스트의 절대 경로에 직접 의존하므로 호환성 문제가 발생할 수 있습니다.

<h6>주요 명령어 및 사용법</h6>

* **바인드 마운트 실행 예시**
  호스트의 /home/user/project 폴더를 컨테이너의 /app 경로와 연결하여 실행
  > docker run -d -v /home/user/project:/app nginx

  * **실무 활용 사례:** 로컬 PC에서 VSCode로 프로젝트 소스코드를 수정하면, 컨테이너 환경에 실시간으로 반영되어 개발 결과를 즉시 확인할 수 있습니다.

---

##### 4.4.5 Tmpfs Mount
호스트의 디스크(HDD/SSD)가 아닌 시스템 메모리(RAM) 영역을 컨테이너에 임시로 마운트하여 사용하는 방식입니다.

* **구조:** `RAM` ➔ `Tmpfs` ➔ `Container`
* **특징:** 파일이 디스크에 기록되지 않고 메모리에서만 처리되므로 처리 속도가 **엄청나게 빠릅니다.**
* **단점:** 컨테이너가 종료되거나 호스트 서버가 재부팅되면 저장되어 있던 데이터가 **전부 삭제(휘발)**되므로 영구 저장이 불가능합니다.
* **주요 사용 사례:** 보안이 중요한 암호화 키/민감 정보 저장, 실시간으로 자주 바뀌는 임시 세션 데이터 관리 시 활용됩니다.

---

##### 4.4.6 Volume vs Bind Mount 비교

| 구분 | Volume (볼륨) | Bind Mount (바인드 마운트) |
| :--- | :--- | :--- |
| **관리 주체** | **Docker**가 직접 관리 | **사용자(호스트 시스템)**가 직접 관리 |
| **호스트 경로** | Docker 자체 관리 영역 사용 (`/var/lib/docker/volumes/`) | 사용자가 지정한 호스트의 임의 경로 사용 |
| **호스트 의존성** | 낮음 (이식성 좋음) | 높음 (호스트 경로 구조에 의존) |
| **추천 용도** | **영구적인 데이터 보존이 필요한 DB 영역**<br>(MySQL, PostgreSQL, Redis, MongoDB 등) | **실시간 변경 및 공유가 필요한 파일 영역**<br>(소스코드 개발, 설정 파일, 로그 수집 등) |
  
</details>

### 5.1 추가 실습 환경 구축

#### 5.1.1 pyenv 설치
* **pyenv란?** 한 서버에서 여러 버전의 파이썬을 독립적으로 관리하고 바꿀 수 있게 해주는 **파이썬 버전 관리자**입니다.
* **도커 실습 전 pyenv를 설치하는 이유:** 도커 컨테이너를 만들기 전, 로컬(호스트) 환경에서 Django 프로젝트 코드를 먼저 생성하고 개발하기 위함입니다.
* **서비스 빌드/배포 흐름:** `Django 코드 작성 (로컬)` ➔ `Docker 이미지 생성` ➔ `Docker 컨테이너 실행`

* **Ubuntu 환경 설치 순서:**
  1. 의존성 패키지 설치
  2. `pyenv` 설치
  3. 환경 변수(`~/.bashrc` 또는 `~/.bash_profile`) 등록
  4. 설정 적용: `source ~/.bashrc`
  5. 버전 확인: `pyenv --version`

#### 5.1.2 pyenv를 활용한 파이썬 가상 환경 구축

| :---: | :--- | :--- | :--- |

| **2** | **프로젝트 디렉터리 생성** | `mkdir django-lab && cd django-lab` | 작업 폴더 생성 및 이동 |

---

##### 🚨 Docker 환경에서의 네트워크 문제와 해결책

* **문제 발생 (`127.0.0.1`):** 도커 컨테이너 내부에서 `127.0.0.1`로 서버를 열면, 루프백(Loopback) IP 특성상 **컨테이너 자기 자신**만 접속할 수 있게 됩니다. 즉, 호스트(PC)나 외부 브라우저에서 컨테이너 안으로 접근이 불가능합니다.
* **해결 방법 (`0.0.0.0`):** 명령어 뒤에 구체적인 IP 대신 **`0.0.0.0:8000`**을 붙여 실행합니다. 이는 **"모든 네트워크 인터페이스(외부 접속 포함)로부터의 요청을 허용하겠다"**는 의미입니다.

```bash
# 외부 접속을 허용하는 Django 실행 명령어
python manage.py runserver 0.0.0.0:8000
```

##### 🌐 포트 포워딩 및 네트워크 구조

도커 컨테이너를 구동할 때는 외부 포트와 컨테이너 내부 포트를 연결하는 **`-p` (포트 포워딩)** 옵션이 필수적입니다.

* **도커 실행 명령어:** `docker run -p 8000:8000 <이미지명>`
* **데이터 전달 구조:**
  `사용자 브라우저 (ubuntu:8000)` ➔ `호스트 포트 (8000)` ➔ `도커 엔진 포트 포워딩` ➔ `Django 컨테이너 (0.0.0.0:8000)`

---

##### 🛡️ Ubuntu 방화벽(UFW) 설정

외부 브라우저에서 접속이 되지 않는다면, 우분투 자체 방화벽에서 8000번 포트를 차단하고 있을 확률이 높습니다. 아래 명령어로 해당 포트를 개방해 주어야 합니다.

| 작업 내용 | 실행 명령어 | 비고 |
| :--- | :--- | :--- |
| **8000번 포트 허용** | `sudo ufw allow 8000` | 외부에서 Django 서버로 접근할 수 있도록 포트 개방 |
| **방화벽 상태 확인** | `sudo ufw status` | 목록에 `8000 ALLOW Anywhere`가 표시되는지 확인 |


## 5.2 YAML 기초
* **YAML이란?** 주로 시스템의 구성이나 환경 설정을 정의할 때 사용하는 데이터 직렬화 양식(설정 파일 형식)입니다.

### 5.2.1 YAML의 개념 및 특징
* **사람 중심의 포맷:** JSON이나 XML에 비해 불필요한 구문 기호(`{}`, `[]`, `<>`)가 적어 사람이 읽고 쓰기 매우 편합니다.
* **⚠️ 주의해야 할 특징:**
  1. **들여쓰기(Indentation) 중심:** 들여쓰기를 통해 데이터의 계층 구조를 판단하므로 엄격하게 맞춰야 합니다.
  2. **탭(Tab) 사용 절대 금지:** 에디터 설정과 관계없이 문법 오류를 유발하므로 **반드시 스페이스바(공백)**로만 들여쓰기를 해야 합니다.
  3. **높은 가독성:** 구조가 한눈에 들어와 복잡한 서비스 설정(Docker Compose 등)도 쉽게 표현할 수 있습니다.

---

### 5.2.2 PyYAML 설치
* **PyYAML 이란?** 파이썬(Python) 프로그램 안에서 YAML 파일을 읽어서(Parsing) 데이터로 쓰거나, 반대로 파이썬 데이터를 YAML 파일로 변환해 주는 라이브러리입니다.
* **설치 및 확인 명령어 (가상환경 활성화 상태 필수):**
  ```bash
  # 라이브러리 설치
  pip install pyyaml

  # 설치 완료 여부 확인
  pip list | grep PyYAML
  ```


## 5.3 도커를 활용한 Django 실행

 ### 5.3.1 도커 호스트에 Django 프로젝트 생성
> ⚠️ **주의:** Docker는 프로그램을 대신 만들어주지 않습니다. Docker는 이미 만들어진 프로그램을 **포장(이미지화)하고 실행(컨테이너화)하는 역할**입니다. 따라서 먼저 호스트 환경에서 Django 프로젝트를 생성해야 합니다. (*여기까지는 Docker와 무관한 과정입니다.*)

* **가상환경 활성화 및 프로젝트 생성 명령어:**
#### 1. 프로젝트 폴더 생성 및 이동
mkdir docker-django && cd docker-django

#### 2. 가상환경 활성화
source venv/bin/activate

#### 3. Django 프로젝트 생성 (현재 폴더 기준)
django-admin startproject config .

#### 4. 로컬 구동 테스트 (정상 작동 확인)
python manage.py runserver 0.0.0.0:8000

---

### 5.3.2 Django 이미지 빌드
> 🐳 **여기서부터 Docker가 등장합니다.** 작성한 코드를 컨테이너로 만들기 위해 이미지를 빌드하는 과정입니다.

#### 1. requirements.txt 생성 
컨테이너 내부 환경에 설치할 파이썬 라이브러리 목록을 기록합니다.
#### 설치된 라이브러리 기록
pip freeze > requirements.txt

#### 생성된 내용 확인
cat requirements.txt

#### 2. Dockerfile 생성
프로젝트 루트 디렉터리에 `Dockerfile`을 생성(`nano Dockerfile`)하고 아래 내용을 작성합니다.

#### 1. 기반이 될 파이썬 공식 이미지 지정
FROM python:3.12

#### 2. 컨테이너 내부에서 명령어가 실행될 작업 디렉터리 설정
WORKDIR /app

#### 3. 라이브러리 설치를 위해 requirements.txt를 컨테이너로 복사
COPY requirements.txt .

#### 4. 이미지 빌드 과정에서 파이썬 패키지 설치
RUN pip install -r requirements.txt

#### 5. 호스트의 현재 디렉터리 파일들을 컨테이너 내부로 전체 복사
COPY . .

#### 6. 컨테이너가 시작될 때 자동으로 실행될 명령어 설정
CMD ["python", "manage.py", "runserver", "0.0.0.0:8000"]

#### 3. 도커 이미지 빌드
작성한 Dockerfile을 기반으로 빌드를 수행합니다.
* **빌드 구조:** Dockerfile -> docker build -> django-app (이미지 생성)

#### 이미지 빌드 (-t 옵션 뒤에 이미지 이름 지정, 끝에 점 '.' 필수)
docker build -t django-app .

#### 생성된 도커 이미지 목록 확인
docker images

---

#### 5.3.3 Django 컨테이너 실행
빌드된 이미지를 바탕으로 독립된 컨테이너를 구동하고 상태를 관리합니다.

| 작업 내용 | 실행 명령어 | 비고 |
| :--- | :--- | :--- |
| **컨테이너 백그라운드 실행** | docker run -d -p 8000:8000 --name django-container django-app | -d: 백그라운드 실행<br>-p: 호스트 8000 포트와 컨테이너 8000 포트 연결 |
| **실행 중인 컨테이너 확인** | docker ps | 컨테이너 ID, 상태(STATUS), 포트 포워딩 정보 확인 |
| **컨테이너 로그 확인** | docker logs django-container | Django 서버의 구동 로그 및 실시간 에러 확인 |


## 5.4 Nginx, Django 연동 후 실행

### 5.4.1 Nginx 컨테이너 실행
Nginx가 정상적으로 구동되는지 확인하기 위해 우선 단독으로 컨테이너를 실행합니다.

# Nginx 공식 이미지를 사용해 백그라운드 실행 (호스트 80 포트 연결)
docker run -d --name nginx -p 80:80 nginx

# 실행 상태 확인
docker ps

---

### 5.4.2 Gunicorn을 통한 연동
> 💡 **Gunicorn이란?** Django 전용 WAS(Web Application Server)입니다. 보안과 성능을 위해 웹 서버(Nginx)와 파이썬 웹 프레임워크(Django) 사이를 중계하는 역할을 합니다.

* **Gunicorn 설치 및 기록:**
호스트 가상환경에서 `gunicorn`을 설치하고 `requirements.txt`에 반영합니다.

# 가상환경에서 gunicorn 설치
pip install gunicorn

# 변경된 패키지 목록을 requirements.txt에 업데이트
pip freeze > requirements.txt

---

### 5.4.3 Django 이미지 빌드
기존 개발용 `runserver` 대신 `gunicorn`을 실행하도록 `Dockerfile`을 수정하고 이미지를 다시 빌드합니다.

#### 1. Dockerfile 수정 (마지막 CMD 부분 변경)
# (앞부분은 동일)
FROM python:3.12
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .

# 개발 서버(runserver) 대신 gunicorn으로 포트 8000번 구동하도록 수정
CMD ["gunicorn", "config.wsgi:application", "--bind", "0.0.0.0:8000"]

#### 2. 이미지 빌드
# 변경된 Dockerfile을 기반으로 django-app 이미지 재빌드
docker build -t django-app .

---

### 5.4.4 Nginx 이미지 빌드
Django 전용 설정이 적용된 Nginx 이미지를 만들기 위해 별도의 폴더와 설정 파일들을 생성합니다.

#### 1. nginx 설정 파일 작성
프로젝트 루트에 `nginx` 폴더를 생성하고, 내부에 `default.conf` 파일을 작성합니다.
mkdir nginx && nano nginx/default.conf

* **nginx/default.conf 내용:**
upstream django {
    server django-app:8000;
}

server {
    listen 80;

    location / {
        proxy_pass http://django;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

#### 2. Nginx Dockerfile 작성
`nginx` 폴더 내부에 `Dockerfile`을 생성(`nano nginx/Dockerfile`)하고 아래 내용을 작성합니다.

# Nginx 공식 이미지 사용
FROM nginx:latest

# 기본 설정 파일을 제거하고 새로 작성한 설정 파일 복사
RUN rm /etc/nginx/conf.d/default.conf
COPY default.conf /etc/nginx/conf.d/

#### 3. Nginx 이미지 빌드
# nginx 폴더로 이동하여 이미지 빌드
cd nginx
docker build -t nginx-app .
cd ..

### 5.4.5 Django와 Nginx 연동 후 컨테이너 실행
독립된 두 컨테이너(Django, Nginx)가 서로 통신할 수 있도록 하나의 가상 네트워크 묶어 실행합니다.

| 순서 | 작업 내용 | 실행 명령어 |
| :--- | :--- | :--- |
| **1** | **도커 가상 네트워크 생성** | docker network create web-network |
| **2** | **Django 컨테이너 실행** | docker run -d --name django-app --network web-network django-app |
| **3** | **Nginx 컨테이너 실행** | docker run -d --name nginx-app --network web-network -p 80:80 nginx-app |

> 📌 **참고:** Django 컨테이너를 실행할 때 `--name django-app`으로 이름을 지정해야 Nginx 설정 파일(`default.conf`)의 `server django-app:8000;` 주소를 통해 도커 내부에서 정상적으로 연결됩니다.

### 5.7 도커 컴포즈를 활용한 컨테이너 실행

#### 5.7.1 도커 컴포즈의 개념
컨테이너 설정을 파일에 적어두자라는 생각에서 나온 것이 Docker Compose입니다.

---

#### 5.7.2 도커 컴포즈 설치
```bash
# 패키지 목록 업데이트

# 도커 컴포즈 v2 설치
sudo apt install -y docker-compose-v2

# 설치 완료 및 버전 확인
docker compose version
```

#### 5.7.3 실습 디렉터리 구성
Docker Compose는 기본적으로 docker-compose.yml 파일을 읽고 컨테이너를 생성합니다.
 ```bash 
  # 폴더 생성
      mkdir compose-lab
      cd compose-lab

   # 파일 생성
      touch docker-compose.yml
  ```


#### 5.7.4 docker-compose.yml 파일 작성

    ```YAML
      services:

        nginx:

          image: nginx

          container_name: my-nginx

          ports:
            - "80:80"
    ```

   * **services :** 컨테이너 목록
* **nginx :** 서비스 이름
* **image :** 사용할 이미지
* **container_name :** 컨테이너 이름
* **ports :** 포트 연결
