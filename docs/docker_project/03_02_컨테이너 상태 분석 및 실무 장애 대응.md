
# 3장 2교시 — Docker 컨테이너 상태 분석 및 장애 대응

## 1. Docker 장애 대응 기본 원칙

컨테이너 장애가 발생하면 무조건 재시작하지 않고 원인을 먼저 분석한다.

### 장애 대응 순서

1. 상태 확인 → `docker ps -a`
2. 로그 분석 → `docker logs`
3. 상세 정보 확인 → `docker inspect`
4. 자원 사용 확인 → `docker stats`
5. 원인 수정 → 설정 변경, 재시작 또는 재생성
6. 정상 동작 검증 → `docker ps`, `curl`

**핵심: 상태 → 로그 → 상세 분석 → 원인 해결 → 재검증**

---

## 2. 컨테이너 상태 및 종료 코드

### 주요 명령어

```bash
# 전체 컨테이너 확인
sudo docker ps -a

# 현재 실행 상태 확인
sudo docker inspect \
  --format '{{.State.Status}}' web01

# 종료 코드 확인
sudo docker inspect \
  --format '{{.State.ExitCode}}' web01

# OOM 종료 여부 확인
sudo docker inspect \
  --format '{{.State.OOMKilled}}' web01
```

### 주요 상태

| 상태 | 의미 |
|---|---|
| Created | 생성되었지만 실행되지 않음 |
| Running | 주 프로세스 실행 중 |
| Exited | 주 프로세스 종료 |
| Restarting | 컨테이너 재시작 진행 중 |

### 주요 Exit Code

| 코드 | 일반적인 의미 |
|---|---|
| 0 | 정상 종료 |
| 1 | 일반적인 프로그램 오류 |
| 125 | Docker 실행 요청 자체의 오류 |
| 126 | 명령어 실행 불가 |
| 127 | 명령어를 찾을 수 없음 |
| 137 | SIGKILL에 의한 종료 가능성 |
| 143 | SIGTERM에 의한 종료 가능성 |

**주의:** ExitCode 137이 반드시 OOM을 의미하지는 않는다.

OOMKilled, 메모리 사용량, 커널 로그 등을 함께 확인해야 한다.

또한 컨테이너가 Running 상태라고 해서 웹서비스까지 정상이라는 의미는 아니다.

## 3. 컨테이너 로그 분석

```bash
# 최근 20줄 조회
sudo docker logs --tail 20 web01

# 최근 10분 로그 조회
sudo docker logs --since 10m web01

# 타임스탬프 포함
sudo docker logs -t --tail 20 web01

# 실시간 로그 추적
sudo docker logs -f web01
```

| 옵션 | 의미 |
|---|---|
| --tail 20 | 마지막 20줄 출력 |
| --since 10m | 최근 10분 로그 조회 |
| -t | 타임스탬프 출력 |
| -f | 실시간 로그 추적 |

- `docker logs`는 컨테이너의 stdout/stderr로 전달된 로그를 조회한다.
- 실시간 추적은 `Ctrl+C`로 종료한다.
- 로그에서 오류 메시지, 발생 시점, 실패한 작업 등을 확인한다.

## 4. CPU·메모리·프로세스 확인

```bash
# 자원 사용량 한 번 조회
sudo docker stats --no-stream web01

# 컨테이너 프로세스 확인
sudo docker top web01

# 컨테이너 주 프로세스의 호스트 PID 조회
sudo docker inspect \
  --format '{{.State.Pid}}' web01
```

### docker stats 주요 항목

| 항목 | 의미 |
|---|---|
| CPU % | CPU 사용률 |
| MEM USAGE / LIMIT | 메모리 사용량 및 제한 |
| MEM % | 메모리 사용률 |
| NET I/O | 네트워크 송수신량 |
| BLOCK I/O | 블록 장치 입출력량 |
| PIDS | 프로세스·스레드 수 |

- `--no-stream`: 자원 정보를 한 번만 조회
- `docker top`: 컨테이너 프로세스 확인
- `State.Pid`: 호스트에서의 컨테이너 주 프로세스 PID

컨테이너 내부 프로세스도 호스트 Linux 커널이 관리한다.

## 5. 장애 실습 ① Nginx 설정 파일 오류

### 장애 재현

존재하지 않는 Nginx 설정 파일을 사용하여 컨테이너를 실행한다.

```bash
sudo docker run -d \
  --name fault-nginx \
  nginx:alpine \
  nginx -g 'daemon off;' \
  -c /etc/nginx/not-found.conf
```

### 옵션 설명

| 설정 | 의미 |
|---|---|
| -d | 컨테이너 백그라운드 실행 |
| --name | 컨테이너 이름 지정 |
| nginx -g 'daemon off;' | Nginx 포그라운드 실행 |
| -c | Nginx 설정 파일 지정 |

### 장애 분석

```bash
sudo docker wait fault-nginx

sudo docker ps -a

sudo docker logs fault-nginx

sudo docker inspect \
  --format 'Status={{.State.Status}} ExitCode={{.State.ExitCode}} OOMKilled={{.State.OOMKilled}}' \
  fault-nginx
```

### 예상 결과

- Status: exited
- ExitCode: 1
- OOMKilled: false
- 로그: Nginx 설정 파일을 열 수 없다는 오류

**장애 원인:** 존재하지 않는 설정 파일로 Nginx를 실행했기 때문.

### 복구

```bash
# 오류 컨테이너 삭제
sudo docker rm fault-nginx

# 정상 설정으로 재생성
sudo docker run -d \
  --name fault-nginx \
  -p 127.0.0.1:18083:80 \
  nginx:alpine

# 정상 동작 확인
curl -I http://127.0.0.1:18083
```

정상 결과: `HTTP/1.1 200 OK`

### 배운 점

- 컨테이너를 재시작한다고 설정 오류가 해결되는 것은 아니다.
- 기존 컨테이너의 잘못된 실행 명령은 재시작해도 유지된다.
- 원인을 수정한 뒤 올바른 설정으로 컨테이너를 재생성해야 한다.

## 6. 장애 실습 ② 호스트 포트 충돌

### 장애 상황

기존 web01이 사용 중인 호스트 포트 18081을 다른 컨테이너에서도 사용하려고 시도한다.

### 장애 재현

```bash
sudo docker run -d \
  --name fault-port \
  -p 127.0.0.1:18081:80 \
  nginx:alpine
```

예상 오류:

`port is already allocated`

### 장애 원인 분석

```bash
# 호스트 포트 사용 확인
sudo ss -lntp | grep ':18081' || true

# Docker 포트 게시 정보 확인
sudo docker ps

# 생성 실패한 컨테이너 확인
sudo docker ps -a --filter name=fault-port
```

**원인:** 동일한 호스트 IP와 TCP 포트를 이미 다른 컨테이너가 사용하고 있기 때문.

### 해결

```bash
# 실패한 컨테이너가 남아 있다면 삭제
sudo docker rm fault-port

# 다른 호스트 포트로 생성
sudo docker run -d \
  --name fault-port \
  -p 127.0.0.1:18084:80 \
  nginx:alpine

# 정상 확인
curl -I http://127.0.0.1:18084
```

정상 결과: `HTTP/1.1 200 OK`

### 배운 점

- 동일한 호스트 IP·TCP 포트 조합을 중복 게시할 수 없다.
- 기존 서비스가 사용 중인 포트를 무작정 해제하면 안 된다.
- 포트 점유 대상을 먼저 확인한 뒤 설정을 변경한다.

## 7. Restart Policy

Restart Policy는 컨테이너 종료 시 자동 재시작 동작을 관리하는 설정이다.

| 정책 | 설명 |
|---|---|
| no | 자동 재시작하지 않음 |
| on-failure | 오류 종료 시 재시작 |
| always | 종료 후 자동 재시작, 수동 중지에는 예외 적용 |
| unless-stopped | 수동 중지 상태는 유지하면서 자동 재시작 |

### 설정 예시

```bash
sudo docker run -d \
  --name example-web \
  --restart unless-stopped \
  nginx:alpine
```

※ 정책 설명용 예시이며 실제 실행 시 같은 이름의 컨테이너가 없는지 확인한다.

### 핵심

- Restart Policy는 서비스 가용성에 도움을 준다.
- Nginx 설정 오류나 DB 연결 오류를 직접 수정하지는 않는다.
- 자동 재시작과 근본 원인 해결은 별개다.

## 8. OOMKilled 이해

OOM(Out Of Memory)은 사용 가능한 메모리가 부족한 상황을 의미한다.

컨테이너 메모리 제한을 초과하는 경우 커널이 프로세스를 종료할 수 있다.

### 확인 명령어

```bash
sudo docker inspect \
  --format '{{.State.ExitCode}} {{.State.OOMKilled}}' web01

sudo docker stats --no-stream web01
```

### 분석 시 주의사항

- ExitCode 137만으로 OOM을 확정하지 않는다.
- OOMKilled 여부를 함께 확인한다.
- 메모리 사용량과 커널 로그도 분석한다.
- 단순 재시작보다 메모리 부족 원인을 해결하는 것이 중요하다.

## 10. 면접 핵심 답변

### Q1. Docker 컨테이너 장애 발생 시 어떻게 대응하나요?

먼저 `docker ps -a`로 컨테이너 상태를 확인하고, `docker logs`로 오류 메시지를 분석합니다.

이후 `docker inspect`로 종료 코드와 OOM 여부 등을 확인하고, 필요하다면 `docker stats`로 자원 사용량을 분석합니다.

원인을 수정한 후 컨테이너를 복구하고 HTTP 요청 등을 통해 정상 동작을 검증합니다.

### Q2. ExitCode 137이면 무조건 OOM인가요?

아닙니다. ExitCode 137은 SIGKILL로 종료되었을 가능성을 의미하며, OOM 외에도 강제 종료 등의 원인이 있을 수 있습니다.

따라서 OOMKilled 여부와 관련 로그를 함께 확인해야 합니다.

### Q3. 컨테이너가 Running인데 서비스 접속이 안 된다면?

Running은 컨테이너 주 프로세스가 실행 중이라는 의미이지 서비스 전체가 정상이라는 의미는 아닙니다.

따라서 애플리케이션 로그, 네트워크 연결, 포트 설정, HTTP 응답 등을 별도로 확인해야 합니다.

### Q4. Docker 컨테이너를 재시작하면 장애가 해결되나요?

일시적인 문제라면 해결될 수 있지만 설정 오류나 잘못된 환경변수처럼 지속되는 원인은 재시작만으로 해결되지 않습니다.

따라서 근본 원인을 분석하고 설정 수정이나 컨테이너 재생성 등의 조치를 취해야 합니다.

## 11. 핵심 암기

- `docker ps -a` = 전체 컨테이너 상태 확인
- `docker logs` = 로그 분석
- `docker inspect` = 상세 상태 및 종료 원인 분석
- `docker stats` = CPU·메모리 사용량 확인
- `docker top` = 컨테이너 프로세스 확인
- ExitCode 0 = 정상 종료
- ExitCode 137 = SIGKILL 가능성, OOM 여부 추가 확인
- Restart Policy = 자동 재시작 정책
- Running ≠ 서비스 정상
- Restart ≠ 근본 원인 해결

### 최종 핵심

> 컨테이너 장애 발생 시 상태 확인 → 로그 분석 → 상세 정보 확인 → 원인 수정 → 복구 → 정상 동작 검증 순서로 대응한다.
